# Phase 1 Persistence Audit

Generated by `pnpm audit:persistence`. The JSON companion is intended for automated comparison in later phases. The migration roadmap and decisions live in [`local-first-migration.md`](./local-first-migration.md).

## Executive summary

Budget App has a useful persistence boundary, but the browser runtime is not local-first yet. The default provider is browser local storage, while shared-server mode replaces that provider with a server-authoritative key/value store. SQLite account, payee, and register adapters exist as validated foundations, but browser runtime configuration cannot select them.

The Shared Platform server stores string values in SQLite, protects the complete key/value namespace with one revision, broadcasts revision invalidations over SSE, and requires clients to reload the authoritative snapshot after remote changes. This is the principal architecture to replace during Phases 2–5.

## Current runtime topology

```text
React UI
  ↓
BudgetPersistenceProvider / AppPersistenceGateway
  ├─ browser-local-storage (default)
  └─ shared-server (deployment option)
       ↓ HTTP key/value operations
Shared Platform server
       ↓
shared-budget.sqlite
```

SQLite domain adapters exist beside this path, but they are not the authoritative browser runtime.

## Read and write paths

### Browser-local mode

Feature services use the active persistence gateway and generic key/value storage, but several features still access `window.localStorage` directly. Large values can spill into IndexedDB through the key/value port. The browser copy is authoritative only on that browser.

### Shared-server mode

The client sends key-level set/remove batches with an expected global revision. The server commits them to `shared_storage`, increments one revision, and announces it through SSE. A revision conflict rejects the complete batch. Remote invalidation causes the client to obtain a current snapshot rather than replaying domain operations.

### SQLite adapter foundation

SQLite adapters already exist for accounts, payees, and substantial register behaviour. They provide the main seam for Phase 2, but unsupported mutations and schema gaps must be resolved before SQLite can become authoritative.

### Attachments

Attachment metadata remains part of register persistence. New attachment content is separated behind an attachment content-store boundary and stored in IndexedDB in the browser. Remote blob transfer, manifests, lifecycle cleanup, and checkpoint integration are not implemented yet.

## Migration constraints

1. No UI feature should need to know whether data is local or synchronised.
2. SQLite must become the local source of truth before incremental sync is introduced.
3. Shared-server mode cannot remain a second authoritative implementation; it must become a sync transport.
4. Direct budget-data localStorage access must move behind repositories or explicit preference stores.
5. Attachments require metadata operations plus separate immutable blob transfer.
6. Existing browser and shared-server budgets need a recoverable migration path and export checkpoint.

## Phase 2 entry criteria

- Choose the browser SQLite runtime (OPFS-backed SQLite or a host-provided SQLite gateway).
- Complete the SQLite schema gap list for all active feature ports.
- Define one authoritative transaction boundary for local writes.
- Classify every direct localStorage use as budget data, migration compatibility, or UI preference.
- Add parity tests that execute the same repository contract against the current and SQLite providers.
- Preserve a one-click export before activating SQLite authority.
