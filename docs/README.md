# Documentation Guide

The repository contains both current architecture documentation and historical
implementation records. Their status should not be inferred from wording
alone.

## Current Architecture

The primary current persistence architecture sources are:

- `architecture/README.md`
- `architecture/local-first-migration.md`
- `local-first-sqlite-architecture.md`
- `architecture/persistence-audit-phase-1.md`
- `architecture/persistence-audit.json`
- `current-codebase-audit.md`

Subsystem architecture documents under `architecture/` remain current when
they are referenced by validation scripts, tests, or the architecture index.

Examples include:

- `architecture/operation-journal.md`
- `architecture/checkpoints.md`
- `architecture/attachment-blob-replication.md`
- `architecture/conflict-resolution.md`
- `architecture/undo-redo.md`

## Architecture Decision Records

Files under `adr/` are architectural decision records. They document decisions
and their rationale and should be retained even when later implementation work
builds on them.

## Historical Release and Migration Records

Version-prefixed documents such as:

- `v119b-persistence-migration-matrix.md`
- `v120-persistence-unification-foundation.md`
- `v122-payees-persistence-port.md`
- `v125-register-persistence-port.md`
- `v149-data-export-backup-restore-preview.md`

describe the repository at specific development milestones.

Older statements about localStorage, missing adapters, or incomplete UI are
expected in these documents and should not be interpreted as descriptions of
the current runtime.

Do not rewrite historical documents merely to match present architecture.

## Generated Documentation

The following files are generated by the persistence audit:

- `architecture/persistence-audit-phase-1.md`
- `architecture/persistence-audit.json`

Regenerate them with:

    pnpm audit:persistence

## Ambiguous Unversioned Documents

Unversioned design, audit, and feature documents outside `architecture/` may
contain either current guidance or historical analysis.

Before modifying or deleting one:

1. check whether scripts or tests reference it;
2. check whether current source code still implements the described contract;
3. preserve it as historical documentation if it records an important
   migration or decision;
4. update or remove it only when its intended role is current and its content
   is demonstrably obsolete.
